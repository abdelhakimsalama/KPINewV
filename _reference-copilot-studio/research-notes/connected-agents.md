## 1. What it is and how it works

Copilot Studio's multi-agent capability ("add other agents") lets one agent delegate work to other agents instead of holding every instruction, tool, and knowledge source itself. There are three distinct constructs, and knowing which is which is the single most important piece of vocabulary in this area:

1. **Child agents** — lightweight agents that exist *inside* the main agent and are fully owned by it. They logically group tools, instructions, and knowledge into clearly defined subagents within one larger agent, and are "ideal for single use cases that respond to a single intent or complete a single task" [OFFICIAL — Learn "Add a child agent"; CAT 2025-09-20 post]. Child agents and topics share the same set of triggers/events; by default a child agent is invoked when the orchestrator matches its *description* ("The agent chooses – Based on description"), and it can be referenced explicitly in the main agent's instructions with a `/` mention [OFFICIAL — Learn "Add a child agent"]. Tools and knowledge are stored at the parent agent but scoped "Available to" the child [OFFICIAL — Learn].

2. **Connected agents (Copilot Studio → Copilot Studio)** — fully independent, separately published Copilot Studio agents that can also run standalone and be reused by multiple main agents [OFFICIAL — CAT 2025-09-20; Learn "Connect to an existing Copilot Studio agent"]. In the new agents experience (GitHub Copilot harness), the mechanism is: the primary agent's orchestration runtime evaluates each user message; if the request aligns with a connected agent's domain (as expressed in its description), the primary agent delegates; the connected agent then runs **in its own orchestration context with its own instructions, knowledge, and tools** and returns its result [OFFICIAL — Learn agents-experience "Connected agents overview" / "Add a connected agent (preview)"]. Routing is description-driven — no custom routing logic or trigger phrases required [OFFICIAL].

3. **External agents** — agents built outside Copilot Studio, connected through one of four channels [OFFICIAL — Learn "Add other agents overview"; CAT 2025-12-02]:
   - **Microsoft Foundry (Azure AI Foundry) agents** — connected via "Connect to an external agent → Microsoft Foundry", authenticated with Microsoft Entra ID, using the Foundry *project endpoint URL*; Copilot Studio auto-creates the connected-agent configuration and the Foundry agent then appears in the agent list like any other agent [CAT 2025-12-16; OFFICIAL — Learn "Connect to a Microsoft Foundry agent (preview)"]. Only agents created in the *new* Foundry portal connect; older-portal agents fail with "404 – Version not found" [OFFICIAL — Learn].
   - **Fabric data agents** — let the Copilot Studio agent reason over enterprise data (warehouse, lakehouse, Power BI semantic model, KQL DB, mirrored DB, ontology). The Fabric data agent must be *published with a rich, detailed description*, the maker needs read access to the data source, and both agents must be **in the same tenant**; cross-geo processing/storing settings may need enabling [OFFICIAL — Learn "Connect to a Microsoft Fabric Data agent (preview)" + Fabric docs "Consume a data agent in Microsoft Copilot Studio (preview)"].
   - **Microsoft 365 Agents SDK agents** — pro-code agents (C#, Python, etc.) reached over the **Activity Protocol** (the Bot Framework lineage protocol); the SDK has built-in support for being called by Copilot Studio [OFFICIAL — Learn "Connect to a Microsoft 365 Agents SDK agent"; CAT 2025-12-13].
   - **Any A2A (Agent2Agent) protocol agent** — framework-agnostic. In Copilot Studio you add an "A2A agent" under the Agents section, supplying the endpoint URL (or the agent-card URL `/.well-known/agent-card.json`), a name/description, and an auth configuration. A2A calls are JSON-RPC 2.0 (`method: "message/send"`); Copilot Studio sends a **rich payload including the complete chat history, locale, IDs and other metadata**, not just the last user message [CAT 2025-12-02; CAT 2025-12-13]. A2A connections "leverage the same custom connector infrastructure, so you can also connect to on-prem A2A agents, or agents under a vNet" [CAT 2025-12-02 — stated as product behavior].

**Inputs and outputs between parent and child/connected agents** [CAT 2025-09-20 — Standard-harness authoring, `agent_edition: standard`]: Inputs/outputs play a dual role — for the *main* agent they inform the orchestrator and let it chain tools and agents (data flow); for the *called* agent they partly define the task ("input: sentence → outputs: sentiment, confidenceLevel"). For **child agents**, inputs/outputs are defined directly in the Copilot Studio UI (under the hood: an `AgentDialog` with root-level `inputType`/`outputType`). For **connected agents**, the main-agent side still required YAML at the time of the post: a `TaskDialog` whose `action` is `InvokeConnectedAgentTaskAction`, with `inputType`/`outputType` **inside the `action` block** (a documented gotcha — different from child agents) and `historyType: ConversationHistory` (i.e., conversation history is passed along). On the connected agent's side, the variables must be made **global**, with "External source can set the value" (inputs) / "External source can receive the value" (outputs) ticked; the agent typically carries an `OnRecognizedIntent` topic for standalone use plus an `OnRedirect` topic that fires when called by another agent. Data returns to the main agent **via the global variable only**; setting `Topic.userRole` in parallel is a pattern to make the value visible to the connected agent's own orchestrator [CAT 2025-09-20]. In the new agents experience, connected-agent delegation is configured conversationally/in the UI without this YAML plumbing [INFERRED from Learn agents-experience docs; exact input/output parity in the new harness: STATUS UNVERIFIED].

**Where this sits in the new component model** [CAT 2026-07-07 — Technical Deep Dive deck]: "every behavior belongs in the smallest component that makes it reliable and inspectable. Instructions carry what's always true, Knowledge the searchable facts, Tools the system actions, Memory the persistent context, Skills the situational procedures, and **connected agents the real specialist domains**." The BlastBox Omega reference sample's flagship scenario ("Block Party Trade-Up") shows a parent agent coordinating specialist agents to settle a messy multi-part request [CAT].

## 2. When to use it / when NOT to use it

**Use multi-agent when:**
- A single agent's tool/instruction surface has grown so large the orchestrator "struggles to reliably differentiate which tool to call" — that's the CAT-stated signal to break the system into purpose-driven agents [CAT 2025-12-16].
- You need **reuse**: one specialist (HR lookup, invoice triage) serving several front-door agents — connected agents, not child agents, are the reuse construct [OFFICIAL — CAT 2025-09-20; Learn agents-experience overview].
- You need **separate ownership**: different teams own, publish, and evolve different agents independently — Learn lists separation of concerns and independent team ownership as core benefits of connected agents [OFFICIAL — Learn agents-experience "Connected agents overview"].
- The specialist already exists **on another stack**: Foundry for pro-code Azure agents, Fabric for the data estate, M365 Agents SDK/Activity Protocol for Microsoft-built pro-code agents, A2A for anything else (LangChain, Semantic Kernel, AutoGen, custom) [OFFICIAL — Learn "Add other agents overview"; CAT 2025-12-02 gives the selection rule: connectors/HTTP tools for plain APIs, MCP for tool/resource-style integrations, Activity Protocol for Microsoft-SDK agents, A2A for cross-platform agents — "all three patterns can coexist in the same Copilot Studio agent"].
- You want to modularize *within* one product boundary without independent publishing overhead → **child agents** ("modularizing logic within your main agent", single intent/single task) [CAT 2025-09-20; OFFICIAL — Learn].

**Do NOT use it when:**
- One agent with good instructions and a modest tool set suffices. Microsoft's own guidance: "Multi-agent orchestration can be powerful, but it's not always necessary and you should consider carefully before adopting a multi-agent approach" [OFFICIAL — Learn "Add other agents overview"].
- The split adds hops without adding genuinely different domains: "If you only have one knowledge source, use a single agent with knowledge instead of splitting into two subagents — multi-agent adds value only when sources are genuinely different" [OFFICIAL — Learn "Multi-agent orchestration patterns and best practices"].
- Latency is critical: each delegation adds orchestration hops (main-agent orchestration identifies the connected agent, then the connected agent runs its **own** orchestration layer) [OFFICIAL — Learn "Add other agents overview"].
- [INFERRED] The "specialist" would be a thin wrapper around a single API call — that is a tool (or MCP server), not an agent; agents earn their place when they must *reason* over their domain (the CAT dad-jokes post's litmus test: "agents that can reason, decide, and act — not just execute a function") [CAT 2025-12-13].

## 3. Classic-experience comparison (what it replaces or simplifies)

- **Replaces Bot Framework Skills and topic-redirect composition.** In classic topic-based authoring, composing bots meant registering Skills (classic quota: 100 skills per agent [OFFICIAL — Learn quotas]) or hand-wiring topic redirects with trigger phrases, plus manual slot-filling of input variables. The new experience replaces that with **description-based LLM routing**: "the platform automatically selects the right agent based on its metadata — no custom logic required" [CAT 2025-12-16]. [INFERRED] The routing decision moves from deterministic trigger-phrase matching to generative orchestration over agent descriptions — more flexible, but quality now depends on how well descriptions are written (see §7).
- **Simplifies inter-agent data flow.** In the Standard-harness era, connected-agent inputs/outputs required maker-authored YAML (`TaskDialog`/`InvokeConnectedAgentTaskAction`), global variables with external-access flags, and `OnRedirect` topics on the callee [CAT 2025-09-20]. Child agents already got a UI for this; the new agents experience configures delegation in the natural-language-first Build surface [OFFICIAL — Learn agents-experience docs].
- **Extends composition beyond Copilot Studio.** Classic composition was essentially Copilot Studio/Bot Framework-internal. The new model federates across Foundry, Fabric, M365 Agents SDK, and any A2A-speaking runtime — low-code and pro-code agents in one orchestrated system [OFFICIAL — Learn "Add other agents overview"; CAT 2025-12-16].
- **New harness re-frames the pieces.** With the GitHub Copilot harness, Copilot Studio was "rebuilt for complex, multi-step work — coordinated, multi-agent systems… where the agent reasons, acts, and adapts in a loop"; connected agents are one of six first-class components (instructions, knowledge, tools, memory, Skills, connected agents), and workflows' component collections also support child agents and MCP [OFFICIAL — techcommunity harness announcement; Learn agents-experience/workflows docs; CAT 2026-07-07]. A migration plugin exists to propose upgrades of Standard-harness agents — CAT explicitly warns to treat its output as a first draft, not to mechanically port every topic ("that's archaeology with YAML") [CAT 2026-07-07].

**Documented limits/requirements (only where a source states them):**
- Copilot Studio→Copilot Studio connected agent: target must be **in the same environment**, **published**, and **configured to allow connections from other agents**; agent **name must be under 30 characters** or the connection fails [OFFICIAL — Learn "Connect to an existing Copilot Studio agent"].

- Latency: multi-agent split "can increase latency due to the extra orchestration hops" [OFFICIAL — Learn "Add other agents overview"].

**Licensing/billing:**
- New-experience agents (GitHub Copilot harness) bill via **Copilot Credits** usage-based billing, covering "LLM tokens, tools (including knowledge and MCPs), and the harness itself" [OFFICIAL — Learn agents-experience "Overview of usage-based billing"]. ## 5. Security and governance implications

- **Admin kill-switch:** Power Platform admin center → Copilot → Settings → **Connected Agents** lets admins enable/disable connected-agent connectivity per environment (part of the preview "channel publishing and connected agent access" governance controls at environment/environment-group level) [OFFICIAL — Learn "Configure channel publishing and connected agent access (preview)"].
- **Callee-side opt-in:** a Copilot Studio agent is only reachable by other agents if its maker configured it to allow connections from other agents [OFFICIAL — Learn]. [INFERRED] This gives per-agent consent semantics, but review it during publishing: an agent exposed to other agents is now an internal API.
- **Conversation history leaves the agent boundary.** Connected-agent invocation can pass conversation history (`historyType: ConversationHistory`) [CAT 2025-09-20], and the A2A payload includes "the complete chat history as well as the locale" and other metadata [CAT 2025-12-02]. [INFERRED] For external/A2A agents this is the headline governance risk: whatever the user has said in the session can be transmitted to an endpoint you may not control. Review data residency, DLP policy coverage, and the endpoint's trust level before connecting; the CAT quickstart's "auth: none" is demo-only.
- **A2A auth and network:** A2A connections ride the custom connector infrastructure, so on-premises/vNet agents are reachable and connector-level auth configurations apply [CAT 2025-12-02; OFFICIAL — Learn "Connect to an agent over the Agent2Agent (A2A) protocol"]. Foundry connections use **Entra ID** ("secure and authenticated cross-agent communication") [CAT 2025-12-16].
- **Identity for agents:** Entra Agent ID (public preview expanded at Ignite 2025) is the direction for giving agents governable identities across these multi-agent meshes [OFFICIAL — Microsoft blog; preview].
- **Observability:** when Copilot Studio calls a Foundry agent, Foundry's trace view shows input received, output generated, conversation/correlation IDs, and completion timestamps — cross-platform debugging is supported [CAT 2025-12-16, stated as product behavior]. On the A2A side, the metadata (IDs, history) can be exploited "for routing, logging, and governance" by the receiving agent [CAT 2025-12-02].
- [INFERRED] Multi-agent systems multiply the audit surface: each agent has its own analytics, transcripts, and publishing lifecycle. Establish per-agent ownership and a naming/description convention early, or incident tracing across the delegation chain becomes archaeology.

## 6. Performance and maintainability implications

- **Latency cost is documented and structural:** every delegation is an extra orchestration hop, and the callee runs its own full orchestration [OFFICIAL — Learn]. [INFERRED] Budget roughly one additional model-planning cycle per hop; deep chains (parent → connected → its connected agent) compound this — keep delegation depth shallow.
- **Accuracy/performance upside:** CAT's stated benefits of decomposition — accuracy (each agent specializes), maintainability (components evolve independently), scalability (add capabilities without bloating one agent), performance ("the orchestrator routes only what's needed") — "one overloaded generalist" vs. "a team of specialists" [CAT 2025-12-16].
- **Tool-selection reliability is the practical trigger:** past ~25–30 tools, orchestrator reliability degrades [OFFICIAL — Learn recommendation]; splitting into specialist agents restores a small, coherent decision space per agent [CAT 2025-12-16 + INFERRED].
- **Maintainability/ownership:** connected agents let different teams own, test, version, and publish their specialist independently; the parent only depends on the callee's *description and contract* (inputs/outputs), not its internals [OFFICIAL — Learn agents-experience benefits list; CAT 2025-09-20]. [INFERRED] Treat the input/output schema + description as the interface; changing them is a breaking change for every parent that connects.
- **Reuse cuts duplication:** one HR specialist reused by n front-door agents beats n copies of HR logic drifting apart [CAT 2025-09-20 scenario; INFERRED generalization].
- [INFERRED] Child agents trade reuse for simplicity: no separate publishing/ALM, one solution artifact, but logic can't be shared across parents. Promote a child agent to a connected agent when a second parent needs it.

## 7. Architecture guidance and anti-patterns

**Guidance (from Microsoft's multi-agent patterns page and CAT practice):**
1. **Single voice:** tell the parent "You're the only agent that communicates with the user. Combine findings from all child agents into a single response," and tell every subagent "You're a subagent. Do NOT reply to the user directly… return your findings to the parent agent" [OFFICIAL — Learn "Multi-agent orchestration patterns and best practices"].
2. **Descriptions are the routing table.** The parent routes on subagent descriptions; "if descriptions are vague, identical, or inaccurate, the parent can't make good routing decisions" [OFFICIAL — Learn]. Fabric requires the data agent be published "with a rich and detailed description" for the same reason [OFFICIAL — Fabric Learn doc].
3. **Make orchestration explicit.** Don't just say "use child agents" — instruct the pattern: invoke, wait for results, combine, then respond [OFFICIAL — Learn].
4. **Pick the right integration primitive** [CAT 2025-12-02]: connectors/HTTP tools for plain APIs; MCP for tool/resource integrations; Activity Protocol for Microsoft-SDK agents; A2A for cross-platform agents; all can coexist in one agent.
5. **Right-size each behavior** [CAT 2026-07-07]: instructions ↔ always-true rules; knowledge ↔ searchable facts; tools ↔ system actions; Skills ↔ situational procedures; connected agents ↔ *real specialist domains*; exact math in code.
6. **Layer low-code + pro-code deliberately:** Copilot Studio as the conversational front door/orchestrator; Foundry/M365 SDK agents for complex reasoning, ML inference, legacy integration; Fabric agents for the data estate [CAT 2025-12-16; CAT 2025-12-13; OFFICIAL — Learn overview].

**Anti-patterns:**
- **The mega-agent:** "An agent shouldn't be one instruction blob with 43 tools and a prayer" [CAT 2026-07-07].
- **Splitting for splitting's sake:** two subagents over one knowledge source adds hops and no value [OFFICIAL — Learn patterns page]; multi-agent "is not always necessary" [OFFICIAL].
- **Wrapping a single API call in an "agent":** if it doesn't need to reason, it's a tool/MCP server, not a connected agent [CAT 2025-12-13 + INFERRED].
- **Vague or overlapping specialist descriptions** → misrouting, double answers (community posts document connected agents each replying); fix with distinct descriptions and the single-voice instructions above [OFFICIAL — Learn; INFERRED].
- **Mechanical migration:** don't turn every classic topic into a Skill and every variable into memory when upgrading to the new harness; re-derive the architecture from the task and run evals on core journeys [CAT 2026-07-07].
- **Unauthenticated external agents in production:** the A2A/dev-tunnel "auth: none" flow is a demo pattern; production needs real auth on the endpoint and a proper connection configuration [CAT 2025-12-02; CAT 2025-12-13].
- [INFERRED] **Deep delegation chains** (parent→child→connected→A2A) multiply latency, failure modes, and audit complexity; prefer a flat hub-and-spoke with one orchestration layer.
