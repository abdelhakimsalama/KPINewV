## 1. What it is and how it works

Security and governance for the new Copilot Studio agents experience spans six control planes: agent authentication, connector consent/OBO, DLP and connector policies, environments + ALM, Power Platform admin center (PPAC) agent management, and cost governance (Copilot Credits / PAYG).

**Agent authentication.** Makers choose among: no authentication, the integrated **"Authenticate with Microsoft"** mode, **manual auth with Entra ID**, or **manual Generic OAuth 2** [OFFICIAL via CAT, `agent-authentication-controls`, `you-dont-need-manual-auth`]. A PPAC admin control — **Authentication for agents** (PPAC > Security > Identity and access), **preview as of June 2026** — sets an environment-level policy that collapses the maker's choices to one of four postures: *No authentication* (anything allowed), *Require Microsoft authentication* (integrated mode only), *Require Entra authentication* (integrated or manual Entra ID), *Allow all supported methods* (everything except anonymous) [OFFICIAL via CAT, citing learn.microsoft.com/power-platform/admin/security/configure-authentication-controls-for-agents]. The mechanism that makes *Require Microsoft authentication* special: with `manual auth`, a Direct Line/WebChat conversation is established **before** sign-in and a maker-editable sign-in message is shown — a pre-authentication content surface. The integrated mode cannot return any response before authentication, so it has no pre-auth surface. Raw Direct Line does not support the integrated mode, so enforcing it makes raw Direct Line clients error before any content is shared, while the **M365 Agents SDK Copilot Studio client** (which rides the same Direct Line channel lever but uses delegated auth) keeps working [OFFICIAL via CAT]. Enforcement is **retroactive**: tightening the policy blocks non-compliant published agents from publishing and stops them responding until fixed [OFFICIAL via CAT].

**Connector consent and OBO.** When an agent invokes a tool/connector configured for **end-user authentication**, the runtime shows a **consent card** ("Connect to continue", Allow/Cancel) asking the user to let the agent create a connection on their behalf. The consent-card experience is only available for connectors that natively support Entra ID authentication; other connectors fall back to the more disruptive **connection manager** dialog [OFFICIAL via CAT, `connector-consent-card-obo`, citing configure-enduser-authentication]. Consent is **expected and (for now) unavoidable** — it is a one-time per-user Allow click, not a misconfiguration symptom [CAT, `obo-for-custom-connectors`]. Custom connectors (and custom MCP servers, which are custom connectors under the hood) can achieve full SSO/OBO — consent card, background connection creation, silent token acquisition — if configured per Microsoft's guidance: app registration for the API/MCP server with exposed scopes; app registration for the custom connector with client secret, consented permissions, and — the most commonly missed step — **Azure API Connections service added as an authorized client**; OAuth settings in the connector; connector shared with users who must exist in the environment [OFFICIAL via CAT, citing learn.microsoft.com/microsoft-copilot-studio/advanced-custom-connector-on-behalf-of]. A telling failure mode: SSO works for the maker (whose connection was created during authoring) but fails for the second user — usually the missing authorized-client step [CAT]. The MCP Onboarding Wizard creates a custom connector in the background; you authenticate in the wizard first, then edit that connector's security settings [OFFICIAL via CAT]. In headless/custom-UI scenarios via the Agents SDK, consent requests arrive as an ordinary Adaptive Card with **no dedicated event type**; developers must detect it heuristically ("Connect to continue" TextBlock + Allow/Cancel Action.Submit buttons) and reply with a message activity carrying `channelData.postBack: true` and `value: {action: "Allow"|"Cancel", id: "submit", shouldAwaitUserInput: true}`. Without that response, Copilot Studio will not invoke end-user-auth connectors [OFFICIAL via CAT, `connector-consent-card-obo`].

**Connection creation prerequisites.** Users can only create/use connections if they exist in the environment's Dataverse with adequate roles. The CAT pattern: one Entra security group per Dataverse security team per environment; assign roles at team level (Environment Maker or custom in Dev, Basic User or restricted in Prod); force-sync membership changes with a Power Automate flow (Office 365 Groups trigger → *Power Platform for Admins – Force Sync User* → Dataverse bound action `SyncGroupMembersToTeam`). Requires a Dataverse-enabled environment; does not apply to Dataverse for Teams environments [CAT, `unlocking-seamless-access…`].

**DLP for agents, tools, and MCP.** Agents' external actions are governed by Power Platform **DLP (Data Policies)** and **Advanced Connector Policies (ACP)** [OFFICIAL via CAT, `compare-mcp-servers-pp-connectors`]. Granularity differs sharply: for **connector-based tools**, admins can block individual actions and set a default allow/block for newly published actions; for **MCP tools, platform-enforced per-tool control is not available** — if an MCP server is allowed, its entire dynamically discovered tool surface is allowed [OFFICIAL via CAT, citing learn.microsoft.com/power-platform/admin/advanced-connector-policies]. What admins can do with MCP: block an entire MCP server as a connector in DLP/ACP, and (connector-dependent) toggle built-in MCP servers that surface as actions on a host connector (e.g., "Microsoft Dataverse MCP Server" on the Dataverse connector). Some MCP servers (e.g., Outlook Mail) respect per-tool DLP, but that is **server-side self-enforcement, not platform enforcement**, and cannot be relied on universally [OFFICIAL via CAT]. Channel access is also DLP-governed via pseudo-connectors: blocking **"Chat without Microsoft Entra ID authentication"** stops anonymous agents; the **Direct Line channels** lever gates raw Direct Line *and* the Agents SDK client together (the coupling the new auth control works around) [OFFICIAL via CAT, `agent-authentication-controls`]. VNet support for select/custom connectors extends to custom MCP servers because they are custom-connector-backed [OFFICIAL via CAT].

**Sandbox boundary (new experience).** Agents on the **GitHub Copilot harness** get a code-execution sandbox (container, Python 3.12.9 observed, ~99 preinstalled libraries) with **no outbound network path**: code cannot call APIs or exfiltrate data regardless of what it imports; all external reach goes through configured Knowledge and Tools, which stay inside DLP/governance controls. The sandbox is ephemeral (not storage) [OFFICIAL via CAT, `copilot-studio-agent-sandbox`].

**Environments and ALM.** The platform baseline: Dev/Test/Prod environment isolation; everything the agent depends on (topics, tools, knowledge sources, custom connectors, connection references, environment variables, flows) authored inside a **solution** in Dev under a **custom publisher/prefix**, set as the **preferred solution**; export **managed** to Test/Prod; promote via **Power Platform Pipelines**, which carry the exact tested artifact forward, bind **connections (via connection references)** and **environment variable values** per environment at deployment time, and record an audit trail with optional approvals. Secrets live in **Azure Key Vault via secret environment variables**, resolved at runtime so rotation needs no redeploy. Managed solutions are not truly sealed — unmanaged layers can override them — so enable **block unmanaged customizations** in Test/Prod and remove maker access. Deployment history is not one-click rollback: uninstalling a managed solution deletes the agent; rollback means redeploying a previous version or restoring a backup [OFFICIAL via CAT, `alm-copilot-studio-agents-foundation`, citing multiple Learn ALM pages]. **Evaluations** (defined test inputs/expected outputs) are the quality gate before export and after import, automatable as a pipeline gate in Azure DevOps [OFFICIAL via CAT].

**Who can build agents / disabling.** Microsoft 365 E3/E5 bundle the **Copilot Studio for Microsoft Teams plan**, delivered via the **`Power Virtual Agents for Office 365`** service plan; it entitles basic-licensed users to build **classic-orchestration** agents in Dataverse for Teams environments publishing to Teams (no generative orchestration, no premium connectors, no other channels). As of **end of June 2026**, the standalone Copilot Studio for Teams app redirects into the Copilot Studio **web app**, making the capability far more visible. The kill switch is disabling that service plan — per user in M365 admin center, or at scale via Entra **group-based licensing**. It blocks create/edit of classic agents but does not delete existing agents or environments, and does not affect standalone Copilot Studio or M365 Copilot license holders [OFFICIAL via CAT, `e3-users-build-agents-turn-it-off`, citing faq-billing-licensing].

**PPAC agent management and cost governance.** GitHub-Copilot-harness agents **consume Copilot Credits during maker design time** (building, previewing, evaluating), before any production lifecycle [OFFICIAL via CAT, `copilot-harness-cost-governance`]. Discovery: **Power Platform Inventory** in PPAC, **Azure Resource Graph**, or the **Inventory API** (`POST api.powerplatform.com/resourcequery/resources/query`), filtering resource type `microsoft.copilotstudio/agents`; the **`isCLIAgent` property identifies harness agents**, returned with environment and owner IDs [OFFICIAL via CAT]. Environment-level controls in **PPAC > Licensing > Copilot Studio > Manage Copilot Credits**: allocate pre-paid credits to an environment; enable/disable **tenant-pool draw**; enable/disable **pay-as-you-go overage**; configure **alert** or **deny** when capacity is exhausted — also settable via the Licensing API (`PATCH /licensing/allocationsByEnvironment`, currency `MCSMessages`, enforcement rules `Alert`/`TenantPool`/`PayGo`/`Deny`) [OFFICIAL via CAT]. Agent-level controls in **Manage Agents**: monthly credit limit, admin notification threshold, stop-at-limit — or `PUT …/entitlements/MCSMessages/resources/<agent>/threshold` with `{limit, notificationThreshold, stopIfOverCapacity, notifyIfOverCapacity, stopResource}`; `stopResource: true` stops the agent immediately regardless of limit [OFFICIAL via CAT]. Agent limits do **not** cap aggregate environment consumption [OFFICIAL via CAT]. PAYG plumbing: **billing policies** link environments to an Azure subscription; **only Production and Sandbox environments are eligible** (not Developer, Trial, Default) [OFFICIAL via CAT, `managing-spend-pay-as-you-go`]. CAT ships a bulk-assignment PowerShell script and an automated budget-breach unlink pipeline (Azure Budget → Action Group webhook → Automation runbook with system-assigned managed identity holding Power Platform Admin rights → Power Automate flow calling `RemoveBillingPolicyEnvironment` per linked environment) [CAT]. Note: Azure Cost Management data lags **8–24 hours** and budget evaluation is periodic, so a runaway agent can spend for hours before the tripwire fires [OFFICIAL via CAT].

## 2. When to use it / when NOT to use it

- **Require Microsoft authentication (admin policy):** use as the default for every environment hosting only employee-facing agents; the SDK client and Teams/M365/SharePoint channels keep working with zero pre-auth exposure [CAT]. Do NOT use for customer-facing/B2C environments that legitimately need anonymous access or non-Entra identity providers (Google, Facebook, custom OAuth) — those need *manual Generic OAuth 2* or anonymous, which the policy blocks [CAT/INFERRED from the policy table].
- **"Authenticate with Microsoft" (maker choice):** the right default for B2E — zero config on Teams/M365 Copilot/SharePoint, one simple app registration for web (`CopilotStudio.Copilots.Invoke` permission), and it unlocks Tenant Graph Grounding. Manual auth remains "mostly useful for B2C" [CAT, `you-dont-need-manual-auth`].
- **Custom connector SSO/OBO:** use whenever an agent must call a custom API or MCP server as the user; do NOT reach for manual auth + `System.User.AccessToken` — manual auth exposes the token to makers and supports only **one OAuth resource** per agent, so you cannot combine Graph-backed knowledge with a custom API token [OFFICIAL via CAT].
- **DLP/ACP for MCP:** use connector-based tools when per-tool admin governance is a requirement; do NOT assume MCP gives you action-level control — it is server-allow/deny only today [OFFICIAL via CAT].
- **Agent-level credit limits:** use as an automatic default for maker-development harness agents; environment allocation + tenant-pool/PAYG toggles are the right lever for funded production. Do NOT treat agent limits as an environment cap (they aren't), and do NOT apply maker-dev defaults to production agents — set production limits from expected usage and criticality [CAT].
- **Full Dev/Test/Prod ALM:** the platform doesn't force it; a throwaway PoC can live in one environment. Adopt the three-environment + managed-solution + pipeline baseline the moment an agent matters to anyone but its maker [CAT].
- **Budget-breach auto-unlink:** use as a backstop, not as fine-grained cost control — the 8–24 h cost-data delay makes it unsuitable for catching fast runaways [OFFICIAL via CAT].

## 3. Classic-experience comparison (what it replaces or simplifies)

- **Auth governance replaces channel-blocking gymnastics.** Classic-era governance blocked the "Chat without Microsoft Entra ID authentication" DLP connector and agonized over the Direct Line channel lever (which breaks the Agents SDK client too). The new *Authentication for agents* control expresses the actual admin intent — an identity posture — instead of a channel/protocol decision, and closes the manual-auth pre-auth content surface that DLP could never reach [OFFICIAL via CAT].
- **Consent card vs connection manager.** The Entra-native consent-card OBO flow (one Allow click, background connection creation) replaces the classic connection-manager interruption and the classic manual-auth pattern of piping `System.User.AccessToken` into HTTP calls — removing maker-visible tokens entirely [OFFICIAL via CAT + CAT].
- **Design-time cost is new.** Classic (standard-harness) agents incurred consumption at runtime; harness agents consume Copilot Credits while makers build/preview/evaluate, which moves the point where admins must apply consumption controls earlier in the lifecycle [OFFICIAL via CAT, `copilot-harness-cost-governance`].
- **Sandboxed execution is new.** Classic agents had no general code execution; the harness sandbox adds it but with a categorical no-egress boundary so the new capability doesn't widen the exfiltration surface beyond DLP-governed Tools/Knowledge [OFFICIAL via CAT].
- **E3 entitlement covers classic only.** The bundled Teams-plan entitlement is limited to classic orchestration; the new experience (generative orchestration/harness) requires proper Copilot Studio licensing — so the "E3 users can suddenly build agents" scare is a classic-agent sprawl issue, not a new-experience cost issue (Teams-plan agents consume no Copilot Credits in Teams) [OFFICIAL via CAT].
- **ALM machinery is unchanged plumbing.** Environments, solutions, publishers, pipelines, connection references, environment variables, Key Vault secrets are the same Power Platform mechanisms as classic; the CAT foundation post presents them as applying to Copilot Studio agents and their components generally. [INFERRED] Harness-specific solution behavior (what exactly of a harness agent — skills, memory config, sandbox artifacts — packages into a solution) is not detailed in the local corpus. ## 5. Security and governance implications

- **The pre-auth surface is a real leak.** With manual auth, maker-authored text renders to *unauthenticated* visitors over Direct Line. Any internal branding, hints about agent purpose, or misconfigured sign-in copy is public. The only structural fix is the integrated auth mode (no pre-auth response path), enforced tenant-wide via *Require Microsoft authentication* [OFFICIAL via CAT; INFERRED on leak severity].
- **Retroactive enforcement is a governance weapon with a blast radius.** Flipping the policy immediately blocks and silences every non-compliant published agent in the environment. CAT's mitigation: inventory first (Copilot Studio Kit "Agent Details" table, *End User Authentication Type* column — anything ≠ `Integrated`, including blank, breaks) [CAT].
- **Manual auth leaks tokens to makers.** `System.User.AccessToken` is visible to authoring; connector-framework OBO keeps tokens out of maker reach entirely — a materially better trust boundary for B2E [OFFICIAL via CAT].
- **The maker-works/user-fails OBO trap** (missing Azure API Connections authorized client) means SSO must be tested with a *second* user before rollout — the maker's own session is not evidence [CAT].
- **MCP is a coarser governance object than connectors.** Its tool surface is discovered dynamically at conversation time, so an allowed server's capabilities can change without any admin action. Treat allowing an MCP server as trusting its publisher's entire current and future tool surface [OFFICIAL via CAT; INFERRED framing].
- **Skills are a trust surface.** Skills shape behavior and can bundle scripts; treat third-party/AI-generated/reused skills as untrusted code — review for prompt injection and tool-misuse instructions before adding [CAT, `modern-mcs-agent-skills`].
- **Sandbox no-egress converts code execution from an exfiltration risk into a contained capability**: only configured Knowledge/Tools cross the boundary, and those are DLP-governed [OFFICIAL via CAT].
- **Cost is now a security-adjacent control.** Design-time credit consumption plus tenant-pool draw means an ungoverned maker environment can silently drain shared capacity; `Deny`/stop-at-limit rules are effectively availability controls for production agents (a stopped agent stops responding) [OFFICIAL via CAT; INFERRED].
- **Identity plumbing is governance plumbing.** The Entra group → Dataverse team → security role chain is where least-privilege is actually implemented per environment (Maker in Dev, Basic User in Prod) [CAT].

## 6. Performance and maintainability implications

- **Consent is a one-time UX tax** per user per connection; after Allow, connections are created and refreshed in the background with no further interruption. OBO configuration is "a little involved, but you only do it once per connector," then every agent reuses it [CAT].
- **User-sync latency breaks first-run experiences.** Dataverse syncs Entra group membership periodically; without the event-driven force-sync flow, newly added users hit permission errors when the agent tries to create a connection. The automated flow removes the human wait [CAT].
- **Pipelines trade ceremony for repeatability**: single-action promotion, exact-artifact promotion Test→Prod, audit trail, approval gates; deployment-time binding of connections/variables removes per-environment hand-editing [OFFICIAL via CAT].
- **Key Vault-referenced secrets rotate without redeployment** [OFFICIAL via CAT].
- **Evaluations as gates** (pre-export and post-import, automatable in Azure DevOps) turn "did the deployment land cleanly" into a checked invariant rather than a hope [CAT].
- **Governance at scale is API-first.** PPAC clicks work for small estates; beyond that, Inventory API/Resource Graph for discovery, Licensing APIs for allocation/limits, and a periodic drift-detection loop (scan → classify → compare against approved controls → remediate) keep configuration honest. Caveat: the allocations PATCH replaces configuration — read-modify-write, or you'll clobber existing enforcement rules [OFFICIAL via CAT].
- **The Azure-based PAYG unlink pipeline carries operational weight** (Automation Account, runbook, Action Group, two permission boundaries, Azure costs); CAT itself flags the complexity and trailed a Power-Platform-native successor [CAT].
- **Consent-card heuristics are a maintenance liability** in custom clients: Microsoft could change card copy/structure and silently break detection [OFFICIAL via CAT on the mechanism; INFERRED on the risk].

## 7. Architecture guidance and anti-patterns

**Guidance:**
1. **Segregate employee-facing and customer-facing agents into different environments**, then set *Require Microsoft authentication* on employee environments from day one. If an environment couldn't survive that policy, your environment strategy — not the policy — is the problem [CAT].
2. **Default to "Authenticate with Microsoft" for B2E**; reserve manual auth for B2C/non-Entra IdPs [CAT].
3. **Route all downstream API access through connector-framework OBO** (first-party connectors, custom connectors, MCP-via-custom-connector), never through manual-auth token plumbing [CAT].
4. **Establish the ALM baseline before the agent matters**: custom publisher/prefix → solution → preferred solution → everything authored inside it → managed export → pipeline → block unmanaged customizations + strip maker access in Test/Prod → evals as gates [CAT].
5. **Classify every environment as maker-development or funded-production and set credit posture accordingly**: maker-dev gets default agent limits, deliberate tenant-pool/PAYG decisions, owner notification, and an escalation path; production gets accountable cost ownership, intentional allocation, and criticality-based limits [CAT].
6. **Automate the loop**: event-driven user sync for connections; inventory-driven drift remediation for environment controls; budget-breach auto-unlink as the spend backstop; group-based licensing for the classic-agent entitlement [CAT].
7. **Prefer connector-based tools when per-action governance is a hard requirement**; when using MCP, govern at the server level and vet the publisher [OFFICIAL via CAT].
8. **Before tightening any retroactive control, measure the blast radius** with Copilot Studio Kit inventory / Power Platform Inventory [CAT].

**Anti-patterns:**
- Authoring in the **default solution** ("the single most common mistake") — components become unpromotable [CAT].
- **Mixing employee- and customer-facing agents in one environment**, making strict auth policy impossible [CAT].
- **Blocking the Direct Line channel lever to close the pre-auth surface** — it also kills the recommended Agents SDK integration; use the auth policy instead [OFFICIAL via CAT].
- **Manual auth for employee scenarios** (token exposure, single OAuth resource, non-solution-aware ALM) [CAT].
- **Relying on an MCP server's self-enforced per-tool DLP compliance** as a control [OFFICIAL via CAT].
- **Treating deployment history as rollback** — uninstalling a managed solution deletes the agent [OFFICIAL via CAT].
- **Hotfixing Test/Prod via unmanaged layers** — silently clobbered on next deploy [OFFICIAL via CAT].
- **Leaving tenant-pool draw enabled by default on new/maker environments**, and **delegating credit allocation to environment admins** without recognizing it's a tenant-wide grant [OFFICIAL via CAT].
- **Assuming agent limits bound environment spend**, or that budget alerts are real-time [OFFICIAL via CAT].
- **Setting `stopResource: true` accidentally** when configuring an agent threshold via API — it stops the agent immediately [OFFICIAL via CAT].
